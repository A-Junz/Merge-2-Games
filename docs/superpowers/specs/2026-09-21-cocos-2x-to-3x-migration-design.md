# Cocos Creator 2.4.13 到 3.8.8 迁移设计

## 目标

在不改写原始 Cocos Creator 2.4.13 工程的前提下，建立一个可由 Cocos Creator 3.8.8 打开的迁移工程，并让主场景 `assets/Scene/Main.fire` 在 Web Preview 中启动。

## 已确认的工程事实

- 原工程目录：`2.x_源码_装扮梦想家园_2.4.13ts/`
- 工程标识：`engine: cocos-creator-js`，`version: 2.4.13`
- 规模：445 个 TypeScript 文件、2 个 `.fire` 场景、67 个 prefab
- 启动场景 UUID：`007a43b6-f8dc-45d5-a373-012937b2de87`
- 依赖范围包含自定义 `packages/`、平台运行时扩展、资源生成脚本和旧版构建配置

## 方案

迁移采用“原工程只读、独立 3.x 工程渐进修复”的双目录方案：

1. 创建迁移工作区，不在原目录执行 Creator 3.x 导入。
2. 通过 Creator 3.8.8 的 `File → Import Cocos Creator 2.x project` 导入 2.x 资源、场景和 prefab。
3. 先验证导入产物是否能打开、资源数据库是否完成、主场景是否可加载。
4. 按错误类别修复脚本：模块/装饰器语法、节点与组件 API、资源加载 API、事件/输入 API、动画与 UI API。
5. 单独处理自定义 packages、平台 SDK 和构建脚本；不把旧平台适配层直接复制为 3.x runtime 代码。
6. 以 Web Preview 作为第一验收目标；移动端和小游戏平台构建放在 Web Preview 稳定后处理。

## 目录与数据流

```text
2.x_源码_装扮梦想家园_2.4.13ts/   原始工程，只读基线
3.8.8-migrated/                    3.x 导入与修复工作区
docs/superpowers/specs/             迁移设计
docs/superpowers/plans/             可执行迁移计划
```

资源数据流为：原工程 `assets/` → 3.8.8 导入器 → 3.x `assets/` 与资源数据库；脚本数据流为：原始 TypeScript → 迁移后的脚本目录 → 3.x 编译检查。原工程的 `library/`、`temp/`、`local/` 不作为迁移源的业务资产，不直接复制为 3.x 运行时状态。

## 兼容性边界

- 2.x 的 `.fire`、prefab、`.meta` 和组件序列化格式由 3.8.8 导入器转换；禁止手工批量替换序列化字段作为第一步。
- 2.x API 与 3.x API 不假设兼容；每次 API 改动必须由编译错误或运行时错误驱动，并保留可回退的小批次。
- 旧版平台 SDK、广告、登录、支付和小游戏适配不作为 Web Preview 的阻塞依赖；迁移初期使用 stub 或平台无关接口隔离它们。
- 迁移产物的工程配置、场景文件和脚本修改只允许发生在 `3.8.8-migrated/`。

## 验收标准

### 必须通过

1. 原始 `project.json` 的 `version` 仍为 `2.4.13`，原工程未被 3.8.8 导入器改写。
2. 3.8.8 能打开迁移工程，资源数据库完成且没有持续导入失败。
3. 迁移工程能加载主场景，并在 Web Preview 中看到游戏画面。
4. 启动阶段没有阻塞性脚本编译错误、场景序列化错误或资源缺失错误。

### 后续阶段

- 登录、广告、支付、小游戏和原生平台 SDK 的真实调用
- Android/iOS/微信小游戏等平台构建
- 与 2.4.13 版本逐功能对照的完整回归

## 风险与回退

- 3.x 迁移是架构变化，不保证一次导入即可运行；若导入器无法处理某类旧资源，保留原文件并对该类资源做最小化手工转换。
- 任一批次修复导致资源数据库或场景不可打开时，删除并重新生成迁移工作区，不触碰原工程。
- 任何无法在当前图形桌面会话完成的导入操作都记录为环境阻塞，不通过直接修改 `project.json` 冒充迁移完成。
